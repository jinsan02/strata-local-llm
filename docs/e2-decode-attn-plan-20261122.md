# E2 엔진 패치 계획: 긴 문맥 디코드 (11-22, KV 정밀도 분석에서)

## 1. 문제

- 64K 실행의 생성 속도가 프롬프트 길이에 따라 크게 떨어진다(x3k64h7 턴 기록, 슬롯 42): 0~5K 77 tok/s · 15~20K 58 · 25~30K 47 · **35~40K 31**. MoE · GDN 은 길이와 무관하므로 늘어나는 시간은 어텐션이다.
- 디코드 어텐션 `k_attn_part`(`src/qwen35/q36_engine.cu`)는 grid (청크, 행 x 쿼리 헤드)로, **쿼리 헤드 16개가 KV 헤드 2개의 fp32 K · V 를 헤드마다 따로 읽는다**(같은 칸을 8번).
- 이론: 1K 토큰당 10층(+ MTP) x 16헤드 x (K + V) 256 x 4B = 약 0.33~0.36 GB → 896 GB/s 에서 0.37~0.40 ms. **실측 기울기 0.55 ms / 1K**. 대역폭에 묶인 중복 읽기로 본다.

## 2. KV 정밀도만 바꾸면 (참고)

- q36 KV 는 fp32 고정, 어텐션 11층(10 + MTP) · KV 헤드 2 · head_dim 256 → 토큰당 44 KiB, 64K 에서 2.75 GiB. 슬롯 1개 = 0.073 GiB.
- fp16: 1.38 GiB → 슬롯 41 → 약 59. int8: 약 69. 그러나 슬롯 효과는 작다(pdiag 11-19, 32K: 슬롯 40 · 63 · 69 에서 8K 입력 71 · 77 · 78, 24K 입력 53 · 57 · 57 tok/s). 실행 기록에서도 슬롯 63 vs 42 는 같은 길이에서 5~6%.

## 3. 패치

| ID | 내용 | 수치 | 기대 |
|---|---|---|---|
| **E2a** | `k_attn_part_gqa<8>`: 한 블록이 KV 헤드 하나의 쿼리 헤드 8개를 맡아 K · V 를 한 번만 읽는다. 헤드마다 계산 순서(HD 내적 · 블록 max/sum · 청크 V 합)는 그대로 | **비트 동일**(설계) | 1K 당 0.55 → 약 0.07 ms. 25K 에서 토큰당 약 27 → 14 ms, 생성 −35~45%(추정) |
| E2b | KV fp16 저장(쓰기 · 디코드 읽기 · 프롬프트의 fp16 사본 생략) | 반올림 차이(손실 없는 변경, RULES 12절) | 슬롯 +18 → 생성 +5~8% |
| (안 함) | KV int8 | 값을 줄임(일반 변경) | E2a · E2b 뒤 남는 이득 작음 |

- E2a 구현(11-22 밤): 엔진 작업 폴더 `work/engine-e2`, 로컬 브랜치 `e2a-gqa-decode`(E1 위, f3704fc41 + 줄 끝 정리), 빌드 `build-e2\strata.exe`. 켜기 `STRATA_Q36_GQA_DECODE=1`(기본 꺼짐). push 안 함.

## 4. 검증 (T2 체인 뒤 자동, `work/stage/e2/e2-post.ps1`, 결과 `engine\e2-post.log`)

1. 수치: q36 solo 게이트로 E0 · E2-off · E2-on 의 greedy 토큰(parity 10개 x 128 + 긴 프롬프트 2K · 12K · 30K x 64, `--mtp 2` 라 검증 창의 여러 행도 지난다). **E2-off = E0, E2-on = E2-off 가 모두 같아야** 한다.
2. 속도: `--bench-pp N --bench-tg 128`, N = 8K · 24K · 40K, 세 구성. E2-off vs E0 은 E1 디코드가 같은 길이에서 약 10% 느렸던 원인(빌드 vs 체크포인트) 확인도 겸한다.
3. 판정: 비트 동일이면 X3 결과도 같으므로 30회 품질 판정 없이 속도만으로 채택(RULES 12절의 수치 검사 = 동일). 다르면 원인을 찾고, E2b 와 묶어 손실 없는 변경 기준으로 30회.

## 5. 위험

- 비트 동일은 컴파일러가 두 커널의 곱셈 · 덧셈을 같은 FMA 로 묶는다는 가정이다. 검증 1 이 확인한다.
- 레지스터 증가(누적 8개 x 3)로 점유율이 떨어질 수 있다. 검증 2 가 확인한다.
