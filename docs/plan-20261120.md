## Q1 근거 갱신 (11-19 저녁)

처음 계획은 'expert 를 작게 해서 VRAM 슬롯을 늘려 빠르게' 였다. 11-19 측정이 이 근거를 약하게 만들었다.

| 측정 | 결과 | 뜻 |
| --- | --- | --- |
| P-diag 1 슬롯 곡선 | 40 슬롯 TG 70.7 · 63 슬롯 75.8~78.6 · 69 슬롯 77.8 (8K) | 63 넘는 슬롯은 속도에 거의 기여 안 함 → **Q1 의 속도 이득은 작다** |
| 메모리 점검 | RAM 31.2GB 중 엔진 상주 약 27GB, 다른 프로그램 합계 약 1GB, 서버 기동 뒤 남은 RAM 0.3~0.5GB, 페이지 파일 최대 7.2GB | 정리할 백그라운드는 없음. **RAM 압박은 엔진 자체(expert 사본 18.75GB)** |
| 64K | 슬롯 42 로 줄고 24K 입력 TG -7%, 48K 입력 24.5 tok/s | 64K 는 RAM · 슬롯 둘 다 부족 |

그래서 Q1 의 목적을 **RAM 여유 확보**로 바꾼다. expert 18.75GB → 13~15GB 면 RAM 4~6GB 가 남고, 같은 VRAM 에 슬롯이 더 들어가 64K 의 슬롯 손실(63 → 42)을 메운다.

바뀌는 것:

1. **관문에 메모리 지표 추가**: 품질(KL · top-1 · X3) 관문은 그대로. 통과한 단계마다 서버 기동 뒤 남은 RAM, 측정 중 페이지 파일 최대치, 32K · 64K 슬롯 수, 64K 24K · 40K · 48K 입력 TG 를 같이 남긴다(k64curve 와 같은 방식).
2. **고르는 기준**: 품질 통과 단계 중 가장 덜 공격적인 것이 기본. 단, 그 단계가 64K 에서 남은 RAM 2GB 이상 · 페이지 파일 증가 없음을 못 맞추면 한 단계 더 공격적인 것을 같은 관문으로 본다.
3. **일정**: BF16 원본(약 70GB) → GGUF 변환은 RAM 을 크게 쓰므로 **서버를 내린 시간에만** 한다(엔진과 같이 돌리면 둘 다 페이지 파일로 밀림). 밤 체인과 겹치지 않게 낮에 서버를 내리고 변환 → 저녁에 품질 측정 순서. '11-20 ~ 22, GPU 와 번갈아' 는 '변환 중에는 GPU 측정 없음' 으로 읽는다.
4. **11-19 밤 k64curve 결과로 갈림**: 48K 급락이 페이지 파일 때문이면(측정 뒤 페이지 파일 사용 증가) Q1 우선순위를 6단계(64K 결정) 앞의 필수로 올린다. 페이지 파일 변화 없이 느리면 원인은 주의(attention) 비용이라 Q1 으로는 못 고치고, 64K 배분안(작업 공간 약 36K)만으로 간다.
5. 6단계 64K 결정은 Q1 이 정해진 뒤 한 번만 한다(두 번 일 안 하기).

사람에게 필요한 것: BF16 원본 약 70GB 다운로드 승인(Q1-1), llama.cpp clone(공식 저장소) 승인(Q1-0), Nsight Systems(필요할 때만),
선택: Defender 검사 시간 · BIOS 정전 후 전원 복구 · BIOS 내장 그래픽 메모리(UMA) 최소(RAM 0.5~0.8GB, 모니터는 5070 Ti 에 그대로).
