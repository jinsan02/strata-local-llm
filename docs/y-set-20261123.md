# Y 세트: 유형이 다른 확인 전용 과제 6개 (11-23)

## 왜

- X3 6과제는 모두 같은 저장소(pypa/packaging) · 같은 유형(명세 읽고 기능 더하기)이다. 30회 넘게 설정을 이 6과제로 골랐으므로(H7 → H9 24/30) 과적합 위험이 크다.
- 실제로 맡길 일에 가까운 유형(버그 고치기 · 테스트 쓰기 · 리팩터링 · 여러 곳 연결 · 다른 저장소)에서도 같은 설정이 통하는지 본다. 계획은 `docs/new-tasks-plan-20261122.md`.
- **확인 전용**: 하네스 튜닝 · 설정 비교에 쓰지 않는다. 기준선을 재고, 채택한 설정이 여기서도 해가 없는지만 본다. 최종 평가(F1)에도 쓰지 않는다.

## 과제 (`configs/eval/y-set/<과제>/`)

| ID | 유형 | 저장소 | 과제 | 채점 |
|---|---|---|---|---|
| `y1_version_postdev_order` | 버그 고치기(보고서) | packaging | 사용자 보고(재현 코드 · 실제 · 기대값)만 준다. `1.0.post1.dev2` 가 `1.0a1` 앞에 정렬되고 `SpecifierSet('>=1.0')` 이 안 받는다. 원인은 보고된 정렬 · 지정자가 아니라 `version._cmpkey` 의 개발판 판정(심은 버그: `post is None` 조건 빠짐) | 숨은 32개(보고 사례 · 이웃 순서 · 지정자) + `test_version` · `test_specifiers` |
| `y2_wheel_build_number` | 버그 고치기(실패 테스트) | packaging | 실패하는 공개 테스트 로그(27줄)를 준다. `parse_wheel_filename` 이 `1000` 빌드 번호를 `(1, '000')` 으로 읽는다(심은 버그: `_build_tag_regex` 가 `\d+?`) | 숨은 12개(여러 자리 · 접미사 · 오류) + `test_utils` |
| `y3_tests_canonicalize_version` | 테스트 쓰기 | packaging | `canonicalize_version` 의 동작을 고정하는 새 테스트 파일 `tests/test_y_canonicalize_version.py` 를 쓴다(이 경로만 `write_allow`) | **돌연변이 채점**: 원본에서 통과 + 돌연변이 10개(`utils` 3 · `_trim_release` 7) 중 7개 이상 잡기 + `test_utils` |
| `y4_refactor_filename_version` | 리팩터링 | packaging | 두 파일 이름 파서의 '버전 파싱 + 예외 바꾸기' 중복을 `_parse_filename_version(version_part, filename, *, error, kind)` 로 뽑기 | 숨은 10개(새 함수 동작 · 두 호출부가 그것을 쓰고 `Version(` · `except InvalidVersion` 이 없음(AST) · 겉 동작 그대로) + `test_utils` |
| `y5_session_cookie_max_age` | 여러 곳 연결 | **flask** | 새 설정 `SESSION_COOKIE_MAX_AGE`: 기본 설정(`app.py`, 1,600줄+) · `SessionInterface.get_cookie_max_age`(형 · 음수 검사) · `save_session` 의 `set_cookie` | 숨은 20개 + `test_session_interface` · `test_basic` · `test_config` |
| `y6_config_require` | 작은 기능(다른 저장소) | **flask** | `Config.require(*keys, allow_none=False)`: 순서 유지 dict, 없는 키를 정렬해 한 번에 `KeyError`, 형 검사 | 숨은 14개 + `test_config` |

- packaging 은 X3 와 같은 고정 커밋 `6a69a83`, flask 는 SWE 세트와 같은 `7ee9ceb`(환경 `swe_flask_5014`, Werkzeug 2.3.7). 처음엔 flask 최신 커밋(49943b5)으로 만들었다가 이 환경의 Werkzeug 가 `partitioned` 를 몰라 기준 커밋부터 회귀 13개가 깨져 바꿨다.
- Y5 회귀에서 `test_basic` 의 3개(`test_session_using_server_name` · `..._and_port` · `test_session_using_session_settings`)는 기준 커밋에서도 실패한다(Werkzeug 2.3.7 의 쿠키 domain 표기 차이, 과제와 무관) → `--deselect`.
- 숨은 테스트 · 참조 패치 · 돌연변이 · 참조 테스트는 `private/` 에 있고 모델 입력과 작업 복사본에 들어가지 않는다(X3 와 같은 규칙). 원 코드는 과제 파일에 복사하지 않고 고정 커밋을 clone 한다. 패치는 `scripts/bench/make_y.py`(편집 정의 → 고정 커밋 사본에 문자열 편집 + `git diff`, Y1 · Y2 지시문의 실제 출력 · 실패 로그도 여기서 채움)로 만들었다.

## 하네스 (`run_x3.py --task-set y`, `g3-chain.ps1 -TaskSet y`)

| 항목 | 내용 |
|---|---|
| 과제 세트 | `--task-set y` → `configs/eval/y-set`. x3 는 예전과 같다(cfg · env 그대로) |
| 과제별 저장소 | `task.json` 의 `repo`(packaging · flask) → 작업 복사본 원본 · 커밋 · 테스트 Python · 시스템 문구의 저장소 이름. Y 세트 실행은 env 에 `repo` · `repo_commit` 을 적는다 |
| `setup_patch` | 작업 복사본을 만든 뒤 과제 패치(버그 심기)를 적용하고 커밋한다(`y-setup`). 모델의 편집 · H8 diff 에 섞이지 않는다 |
| `write_allow` | `tests/` 아래라도 이 경로만은 만들 · 고칠 수 있다(Y3) |
| 돌연변이 채점 | `grade: mutants` → 회귀 + 쓴 테스트가 원본에서 1개 이상 통과 + `private/mutants/*.patch` 를 하나씩 `git apply` 해서 쓴 테스트가 실패하면 잡음. 통과 = 잡은 수 ≥ `kill_min`(7/10). 원장 `tests_passed` 는 잡은 수/10 |

|---|---|---|

- **한계(y3)**: 저장소 기존 테스트를 통째로 베끼면 통과한다. 기존 테스트가 `canonicalize_version` 을 촘촘히 다루기 때문이다. 이 과제는 '지금 코드에서 통과하는, 의미 있는 테스트 파일을 만들 수 있나'를 보는 것으로 읽는다. 더 어려운 테스트 쓰기 과제는 기존 테스트가 약한 함수로 나중에 더한다.
- 하네스 점검 `scripts/bench/selftest_y.py`(가짜 모델): setup 커밋 · 깨끗한 작업 트리, Y3 허용 경로만 쓰기 · 참조 테스트 10/10, flask 과제에 edit_file 로 참조 구현 → 14/14, x3 기본값 그대로 — 7/7. 기존 selftest 12종도 통과.
