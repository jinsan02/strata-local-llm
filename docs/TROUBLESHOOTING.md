## T-009 원장 kv 열이 실제(FP32)와 다른 int8 로 기록됨
- 날짜 · 단계 · 영역: 11-18 · 계획 v2.2 KV 확인 · bench
- 상태: 해결 (정정 기록)
### 발생 로그
원장 전 행 `kv=int8`. 서버 설정 `strata-qwen36-ctx*.json` 인자에 `--kv` 없음.
### 상황 분석
러너 기본값을 Flash-Next 런처 기본값(int8)에서 가져왔다. q36 경로는 `--kv` 를 읽지 않고 K · V 를 FP32 로 할당(`q36_engine.cu` 1320~1333), prompt attention 용 FP16 사본(1393) [문서·코드]. 실제 할당 바이트는 아직 로그로 안 봄.
### 영향
측정값은 유효. `kv` 열만 틀림. KV 정밀도 비교를 1차(옵션)로 하려던 계획(Q3)이 불가 → 3차(엔진) 과제.
### 개선·조치
러너 기본값 `fp32`, `docs/LEDGER_SCHEMA.md` 정정 기록. 원장 행은 고치지 않는다 (append-only).
### 재발 방지
설정 열은 서버 설정 · 엔진 로그에서 읽어 채우고 상수로 적지 않는다 (다음 러너 개선 때).

## T-008 긴 입력에서 코드에 `]]` 문법 오류
- 날짜 · 단계 · 영역: 11-18 · X2 · eval, (추정) quant · sampling
- 상태: 토의 필요
### 발생 로그
`x2_…_in16k_topo_sort_b8k_r2`, `x2_…_in24k_topo_sort_b8k_r3`: 0/6, pytest `1 error`(수집 실패). 두 답 모두 함수 서명이 `-> List[str]]:` / `-> list[str]]:` — 닫는 괄호 하나가 더 붙음. 설명 · 알고리즘은 맞다.
### 상황 분석
같은 과제가 짧은 입력(XB 2차 9회, X2 2K · 8K 12회)에서는 한 번도 이렇게 틀리지 않았다. 입력 16K · 24K 에서만 2/12. 가설 (모두 미확인): (1) temperature 1.0 샘플링에서 `]]` 토큰이 뽑힘 (2) 긴 컨텍스트에서 4비트 가중치 · int8 KV 정밀도 영향 (3) 우연(표본 작음).
### 영향
품질 지표가 문법 실수 하나로 0점이 된다. 실사용에서는 클라이언트가 테스트 실패를 보고 고칠 수 있는 종류.
### 개선·조치
후보: 같은 프롬프트를 seed 만 바꿔 여러 번(빈도 확인), greedy · 낮은 temperature 비교(Q11 과 함께), KV 형식 비교(Q3), M1 양자화 비교. 정해지기 전까지 기록만.
### 재발 방지
X3 이상에서는 문법 오류 실패를 '문법' 으로 따로 분류해 센다 (미적용).

## T-007 출력 예산이 사실상 thinking 상한 (answer_room)
- 날짜 · 단계 · 영역: 11-18 · XB 2차 · engine, eval
- 상태: 조치 중 — 토의 결과 (b) 방향 (11-18)
### 발생 로그
XB 2차(`xb2_*`)에서 4K 예산의 parse_duration 3회가 모두 `finish_reason=stop` 인데 10~13/16 통과. 2K·8K 는 대부분 16/16. 출력 토큰이 3,439~3,465 로 4,096 보다 조금 작은 곳에 몰림.
### 상황 분석
`serve/server.py:6235`: thinking 요청에 예산이 없고 `max_tokens ≥ 1024` 이면 thinking 을 `max_tokens − max(512, max_tokens/4)` 에서 닫는다(`answer_room`, 기본 켜짐). 2K→1,536 · 4K→3,072 · 8K→6,144. parse_duration 은 8K 에서 3.9K~6.5K 토큰을 썼으므로 4K 에서는 생각이 끊긴 채 답했다고 본다 (추정 — 같은 과제를 answer_room 끄고 재면 확인).
### 영향
XB 는 '출력 예산 시험' 이 아니라 'thinking 상한 시험' 으로 읽어야 한다. 클라이언트 max_tokens 가 품질을 직접 바꾼다.
### 개선·조치
현재: 운영 예산 8,192. 선택지: (a) 그대로 (b) `reasoning_budget_tokens` 명시 (c) `"answer_room": false`.

**토의 결과 (11-18, 사용자 · Claude):** (b) 를 우선 고려한다. (c) 는 thinking 이 max_tokens 에 닿으면 답변 0 으로 끝날 수 있어 제외. (a) 는 답변 몫이 max_tokens/4(8K → 2,048)로 고정돼 파일 전체 쓰기 · 긴 diff 같은 실제 코딩 답변이 잘릴 수 있다. (b) 는 서버 설정(`runconfig.py` 의 `reasoning_budget_tokens`)으로 클라이언트(Claude Code 의 thinking budget, Codex 의 effort)와 무관하게 thinking 과 답변 몫을 따로 정할 수 있다. 전환 전까지 운영은 (a).

**검증 계획 (B1):** max_tokens 8,192 고정, thinking 상한 3K · 4.5K · 6K(= 현재 a). 과제는 탐색 4개 + 답변이 긴 과제(여러 파일 수정 · 긴 코드) 추가. 기록: 통과, thinking 사용량, 답변 잘림, 첫 답변 지연. X2 에서 parse_duration 이 출력 6.6K 까지 써서 상한 6,144 근처였으므로 상한을 늘려야 하는 과제가 있는지도 본다.
### 재발 방지
러너 config 에 서버의 thinking 상한을 같이 기록한다 (미적용).
