# E1 후보 · 64K 메모 (2026-11-19, 엔진 소스 읽기)

E0 = STRATA v0.2.15 `c775728`, q36 경로(`engine/src/qwen35/q36_engine.cu`). 측정 전 설계 메모이고 수치는 소스 · 로그에서 읽은 것이다.

## 1. 대화 재사용 (T-013) — 프롬프트 끝 순환 상태 스냅샷

**지금 동작** (`match_len` 3544, 요청 처리 3651): 세션이 든 토큰 전체(이전 프롬프트 + 생성 토큰, 받아들인 MTP 초안 포함)가
새 프롬프트의 앞부분과 정확히 같을 때만 그 길이를 재사용, 아니면 `E.reset()` 후 처음부터. 중간 체크포인트가 없다.
`--conversation-cache-mib` 등은 q36 경로에 없다(로그 'not an option of this engine').

**왜 자주 어긋나나**: 클라이언트 · 하네스가 이전 답을 다시 보낼 때 템플릿이 thinking 을 빼거나 도구 호출 JSON 을 다르게
렌더링하면 이전 생성 구간 첫 토큰에서 어긋난다. 어긋난 지점 앞(= 이전 요청의 프롬프트 전체)은 같은데도 버린다.

**제안**: 요청마다 생성을 시작하기 직전(프롬프트를 다 읽은 시점)의 순환 상태를 세션별로 하나 보관한다.
다음 요청이 그 지점까지 같으면 (a) attention 레이어 KV 는 그 위치로 자르고(뒤 칸은 덮어쓰면 됨), (b) 순환(GDN) 상태는
스냅샷으로 되돌리고, (c) 그 뒤부터 읽는다.

**비용 추정** (소스 1542 의 세션 크기 식): 순환 상태 = `ssm_v_heads x ssm_state_size^2 x 4 B x GDN 레이어 수`.
Qwen3.6-35B-A3B 값(헤드 32 · 상태 128 · GDN 30층으로 가정, 엔진 로그로 확인 필요)이면 약 63MB + conv 상태(작음).
VRAM 복사 한 번(수 ms)이라 측정 영향은 작다. KV 는 이미 있으므로 추가 메모리는 스냅샷뿐.

**기대 효과**: 하네스가 생성 그대로 다시 보내지 않아도(H0 · 클라이언트 렌더링 차이) 이전 프롬프트 전체를 재사용.
H2a 가 정확한 재전송으로 얻은 재읽기 −83% 에 가까운 효과를 클라이언트 쪽 협조 없이 얻는다(가설).
**확인 순서**: 업스트림에 같은 기능 · 이슈가 있는지 → E1 브랜치에서 구현 → probe_cache(tools_all · reencode) 재사용 0 → 큰 값.

## 2. 64K (Q16)

| 항목 | 소스 · 로그에서 확인한 것 |
| --- | --- |
| KV 정밀도 | q36 은 **fp32 고정**. `--kv int8 · q4_0 · k8v4 · --kv-grow · --kv-resident` 는 이 경로 옵션이 아니다(무시됨) |
| KV 크기 식 | `n_head_kv x head_dim x 2 x 4 B x ctx x (attention 레이어 + MTP 블록)` |
| VRAM 여유 (로딩 로그) | 8K 7.67 · 16K 7.25 · 32K 6.50GiB → 1K 칸당 약 0.047GiB, 64K 는 약 5.0GiB(추정) |
| VRAM 상주 expert | 8K 79 · 16K 74 · 32K 63 /256 → 64K 약 42 (추정) |
| 받는 메모리 옵션 | `--expert-vram GiB` · `--expert-slots N` · `--hybrid-rows` · `--cpu-threads` · `--batch` |
| RAM | 32K 에서 이미 남은 RAM 0.2~1.0GB · 페이지 파일 1~2.6GB 사용(11-19 cache_ab). KV 가 VRAM 이라 64K 가 RAM 을 크게 늘리진 않겠지만 여유가 없다 |

**결론**: 64K 에서 KV 를 줄일 설정은 없다. 비용은 상주 expert 감소(생성 속도)이고, 줄이려면 E1(KV int8 를 q36 에 이식 —
TurboQuant 메모 v2.2 9.7: 이 모델은 KV 비중이 작아 이득 상한 약 1.1GiB @32K, 64K 면 약 2배) 또는 출력 예산 조정.
64K 측정 전 페이지 파일 확대 권장(아래 plan 부록).
