# 루프 · 멀티 턴 · 캐시 계획 (L 계열, 2026-11-19 초안)

목표: 코딩 에이전트에 **고치고 → 테스트하고 → 다시 고치는 루프**와 **일을 맡기고 → 받고 → 다시 맡기는 반복**을 넣는다.
조건은 사용자 결정(11-19)을 따른다: 정확도 우선, 손실 없는 것 먼저, 측정 중에는 추적 경로를 건드리지 않는다.

## 0. 지금 구조 (사실)

## 1. 캐시가 깨지는 지점 (루프에서 비용이 되는 곳)

| # | 지점 | 지금 영향 | 대책 |
| --- | --- | --- | --- |
| K1 | reasoning 을 안 보냄(H0) | 매 턴 전체 다시 처리 (H0 새 입력 100K~250K/과제) | H2a/H3 정확 재전송 (채택 판정 중) |
| K2 | **강제 턴에서 도구 목록이 바뀜** (전부 → 없음 · edit 만) | 도구 정의는 프롬프트 앞쪽에 있으므로 강제 턴 1번에 ~22K 전부 다시 처리 (Qwen 템플릿 기준 추정, L0 에서 턴별 cache_n 으로 확인) | L3: 도구 목록은 그대로, 하네스가 거절 메시지로 막기 |
| K3 | 워커 보완 시 대화를 새로 만듦 | 탐색 결과를 잃고 처음부터 다시 읽음 | L4: 같은 대화에 테스트 실패를 이어 붙임 |
| K4 | 과제가 바뀜 (다음 위임) | 공통 시스템 프롬프트 · 도구 정의(~2~3K)도 다시 처리. 작음 | E1a 스냅샷이 있으면 공짜 |
| K5 | 히스토리 압축 · 마스킹 (Claude Code 자동 압축 포함) | 압축 1번마다 전체 다시 처리 | 압축은 한 번에 몰아서(L2), E1a |
| K6 | 재토큰화 불일치 | 드물게 재사용 실패 | A4 (`serve/server.py` 토큰 id 이어 붙이기) |

## 2. 실험 항목

| ID | 내용 | 손실 | 측정 | 판정 | 시점 |
| --- | --- | --- | --- | --- | --- |
| **L0** | 캐시 · 예산 분석기: 턴별 `cache_n / prompt_tokens`, 재처리 지점(K1~K5) 분류, 강제 턴 원인, 테스트 출력이 차지한 토큰 | 없음 (기존 로그) | 오늘 밤 hadd 로그 전체 | 지표만 | 11-20 오전 (CPU) |
| **L1** | 안쪽 테스트 루프 (B+RT) | 없음 | X3 3과제 x 4회: 통과 · tests_runs · max_in · forced_turns | 대조 -1 이내 | **11-19 밤 (예정됨)** |
| **L3** | 강제 턴 도구 목록 고정 (막기는 하네스가 '도구 사용 불가' 결과로) | 캐시 손실 없음. 행동은 약간 바뀔 수 있음 | 강제 턴 재처리 시간 · 통과 | -1 이내 + 재처리 감소 | 11-20 밤 |
| **L4** | 워커 보완을 같은 대화로 이어 붙이기 (새 대화 vs 이어 붙이기) | 없음 (오히려 정보 보존) | X3 + test_cmd, 보완 성공률 · 시간 · 새 입력 | -1 이내, 보완 성공 증가 | 11-20 밤 |
| **L2** | 테스트 출력 정리: 최신 결과만 원문, 이전 결과는 한 줄 요약. 입력이 문턱(예 18K)을 넘을 때 **한 번에** 적용 | 손실 가능 | 통과 · 강제 턴 감소 | 엄격 관문 (-1 이내, 확인 전용 D·E·F 포함) | L1 결과가 '예산 부족' 일 때만 |
| **L5** | 일 반복: 같은 저장소에 위임 3~5건 연속 · 후속 지시 (`delegate_followup`: 저장된 대화 + 피드백, 서버가 상태를 들고 있으면 재사용) | 없음 | 과제당 시간 · 재처리 · VRAM/RAM 변화 · 서버 안정성 | 회귀 없음 · 누수 없음 | X4 단계 (11-24) |
| **L6** | 주 에이전트 긴 세션 (Claude Code → 로컬, 30턴 이상, 자동 압축 포함) | 없음 | 압축 횟수 · 재처리 시간 · 완료율 | 실제 작업 회귀 없음 | X4 단계 |
| **L7** | 루프 + 64K | 없음 | RT 를 32K vs 64K | 64K 결정(단계 6)에 포함 | 11-23 |

E1a 스냅샷(업스트림 #3909)은 K2 · K4 · K5 를 근본적으로 줄이므로 L2 · L5 · L6 보다 먼저 들어오는 것이 좋다 (E1 단계 1순위 그대로).

## 3. 순서

1. 11-19 밤: L1 (hadd 의 B+RT 팔) — 이미 체인에 있음.
2. 11-20 오전: L0 분석 (CPU) → 루프가 문맥 예산을 얼마나 먹는지, 강제 턴 재처리가 몇 초인지 숫자로 확인.
3. 11-20 낮: L3 · L4 구현 (stage 에서) + 자체 점검. 같은 날 E1a 이식 시작.
4. 11-20 밤: L3 · L4 A/B (공유 대조, X3 3과제 x 4회).
5. L1 결과가 '예산 부족 · 강제 턴 증가' 면 L2 를 엄격 관문으로 추가.
6. X4 (11-24): L5 · L6 — 실제 경로에서 반복 위임 · 긴 세션.
7. 64K 결정(11-23)에 L7 포함.

## 4. 판정 원칙

- 손실 없는 L0 · L1 · L3 · L4 · L5 · L6 은 하네스 채택 기준(대조 -1 이내, 회귀 증가 없음) 그대로.
- 손실 가능한 L2 는 확인 전용 D · E · F 15회에서도 -1 이내일 때만.
- 정확도가 같으면 그다음에 시간 · 새 입력 · 재처리 횟수.
