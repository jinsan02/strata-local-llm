## 1. 추진 목적

대상 PC에서 STRATA를 실행하고, Codex 또는 Claude Code가 하드웨어 정보와 프로파일링 결과를 근거로 추론 설정, 모델 양자화 배분, 엔진 코드를 수정·측정하는 실험 체계를 구축한다.

목표는 한국어·코딩 품질을 유지하면서 첫 답변 지연, 실제 답변 완료 시간, 생성 처리량, VRAM·RAM 사용량을 개선하는 것이다. 개선이 검증된 변경만 운영 구성에 반영하고, 개선이 없는 경우에도 재현 가능한 기준선과 실패 기록을 남긴다.

## 3. STRATA 및 모델 호환성 사전 검증

### 3.1 엔진 식별

이 기획서에서 STRATA는 [Niko1221/Strata](https://github.com/Niko1221/Strata)를 뜻한다. 동명의 다른 엔진이나 포크와 결과를 혼합하지 않는다. 소스 URL, 릴리스, 커밋, 빌드 옵션, CUDA·컴파일러 버전과 의존성 리비전을 기록한다.

### 3.2 모델 선정 원칙

기존 Qwen3-14B Q5_K_M은 필수 모델 조건에서 제외한다. GGUF 확장자가 같아도 STRATA의 아키텍처·팩·커널 지원을 충족해야 한다.

확인한 공식 문서가 다루는 모델 계열은 Qwen3.8-Flash-Next 및 Qwen3.6-35B-A3B다. 지원 범위는 착수 시 고정한 리비전에서 재확인한다. [지원 모델 문서](https://github.com/Niko1221/Strata/blob/main/docs/MODELS.md)

| 후보 | 검토 목적 | 채택 조건 |
| --- | --- | --- |
| Qwen3.6-35B-A3B의 지원 양자화 | 상대적으로 작은 지원 모델을 우선 검토 | 모델 실행 계획·실측 메모리·한국어·코딩 품질 통과 |
| Flash-Next Coder 계열 | 제한된 메모리에서 코딩 용도 검토 | 일반 한국어 품질과 모델 변경 효과를 별도 평가 |
| 기타 지원 저메모리 팩 | 위 후보가 적합하지 않을 때 비교 | 저장 공간·SSD 의존도·지연이 사용 목적에 적합 |

후보 이름은 검토 목록이며 운영 모델 확정이 아니다. 모델별 데이터는 별도 기준선을 갖고, 모델 교체에 따른 변화와 최적화 효과를 구분한다.

### 3.3 착수 게이트

1. 설치된 엔진에서 지원 아키텍처·양자화·Windows CUDA 경로를 확인한다.
2. 다운로드 전 실행 계획과 파일 목록·크기·메모리 예산을 확인한다.
3. CPU 정보, 가용 RAM, SSD 여유 공간·속도를 포함해 실제 자원 조건을 기록한다.
4. 한 후보를 로딩하여 목표 8K 조건과 로컬 API 응답을 검증한다.
5. 기본 한국어·코딩 점검을 통과한 후보를 기준 모델 M0로 고정한다.

16GB VRAM과 RAM 32GB를 단순 합산해 적재 가능성을 판단하지 않는다. OS·KV·버퍼·파일 캐시·중복 적재까지 실측한다. 8K를 충족하지 못하면 축소 조건은 진단용으로만 기록하고 8K 목표 달성으로 처리하지 않는다. 적합한 후보가 없으면 원인과 필요한 변경을 보고하며, 다른 엔진으로 자동 대체하지 않는다.

## 4. 양자화 규격과 동적 동작의 구분

### 4.1 기본 실험: 사전에 결정하는 혼합 정밀도

에이전트가 레이어·텐서별 정밀도 배분을 제안하고, 유효한 GGUF와 STRATA가 요구하는 팩을 생성한 후 재로딩하여 평가한다. 한 레이어 안에서도 attention·FFN·expert 관련 텐서에 서로 다른 저장 형식을 적용할 수 있지만, 선택한 모델 경로가 그 조합을 실제로 지원해야 한다.

공식 커널 표에는 expert 역할에 따른 Q4_K·Q5_K·Q6_K·Q5_1·Q8_0 경로가 제시되어 있다. 이는 모든 텐서·모델에서 임의 조합이 허용된다는 뜻이 아니다. [형식과 커널 지원표](https://github.com/Niko1221/Strata/blob/main/docs/QUANTS.md)

| 규격 항목 | 준수 조건 |
| --- | --- |
| 아키텍처 및 메타데이터 | 엔진이 기대하는 구조·차원·라우팅 정보를 보존 |
| 텐서 식별 | 실제 파일의 이름·shape·역할을 기준으로 변경 대상을 지정 |
| 데이터 형식 | 지원되는 타입의 블록 크기·스케일·패킹·정렬을 준수 |
| 모델 구성 이름 | Q4_K_M·UD-Q4_K_XL 같은 배포 이름과 개별 텐서 타입을 구분 |
| 팩 생성 | 채택 리비전의 변환 도구가 요구하는 인덱스·레이아웃·부속 파일 유지 |
| 실행 경로 | CPU·CUDA 및 prefill·decode에서 모두 해당 텐서를 처리할 수 있는지 검증 |
| 파일 검증 | 헤더·shape·크기·해시·로딩·최소 추론 검사를 통과 |

GGUF 규격과 양자화 도구는 [GGUF 명세](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md), [llama.cpp 양자화 문서](https://github.com/ggml-org/llama.cpp/tree/master/tools/quantize)를 참고한다. llama.cpp는 변환·분석 보조 도구로 사용할 수 있으며 운영 추론 엔진은 STRATA로 유지한다.

### 4.2 실행 중 동작

| 동작 | 본 실험에서의 처리 |
| --- | --- |
| 대화에 따라 expert의 RAM·VRAM 배치 변경 | STRATA의 지원 기능을 확인해 튜닝 |
| 레이어별로 다른 비트 수를 저장한 모델 실행 | 맞춤 양자화 실험의 기본 방식 |
| 질문·토큰별 Q4↔Q8 자동 전환 | 기본 지원으로 가정하지 않고 별도 엔진 개발 과제로 분리 |
| 실행 시 activation·KV 양자화 | 가중치 저장 정밀도와 별도 변수로 기록·평가 |

실행 중 저정밀 가중치를 고정밀로 캐스팅해도 이미 잃은 정보가 복원되지는 않는다. 실제 고정밀 전환을 구현하려면 고정밀 원본 또는 복수 표현, 메모리 예산, 변환·전송 비용, 커널 선택과 동기화가 필요하다.

## 5. AI 에이전트의 역할과 작업 방식

Codex 또는 Claude Code를 주 실행자로 사용한다. 두 도구를 비교할 때에는 별도 브랜치·실험 ID를 사용하고 모델·엔진 파일을 동시에 수정하지 않는다. 원격 에이전트가 직접 GPU를 사용할 수 없는 환경에서는 대상 Windows PC의 실행 도구를 통해 측정 결과를 받아야 한다.

### 5.1 반복 최적화 절차

1. 현재 기준선과 프로파일을 읽고 병목 하나를 지정한다.
2. 변경 이유, 대상 파일·텐서, 기대 지표, 품질 위험, 확인 방법을 기록한다.
3. 후보 설정·양자화 또는 엔진 패치를 만든다.
4. 파일 호환성·빌드·수치 정확성·최소 추론 검사를 먼저 수행한다.
5. 같은 PC에서 기준선과 후보를 번갈아 측정한다.
6. 탐색용 품질 평가와 지연·메모리 결과를 비교한다.
7. 개선이 검증되면 후보로 보존하고, 실패·퇴행 시 실행 구성을 복원한다.
8. 원시 데이터와 실패 이유를 기록한 뒤 다음 가설로 진행한다.

에이전트가 변경할 수 있는 것은 후보 모델·엔진·실행 설정이다. 최종 평가 정답, 측정 시계, 채점 기준, 원시 결과, 비교 기준선을 수정하여 수치를 높이는 행동은 허용하지 않는다. 평가 도구에 결함이 발견되면 수정 버전을 기록하고 기준선과 후보를 모두 재측정한다.

### 5.2 탐색 예산안

- 단계별 최대 20개 후보, 5개 후보마다 결과를 검토한다.
- 엔진·설정 탐색은 회당 최대 2시간을 초기 예산으로 한다. 양자화 변환·평가 시간은 별도로 추정하고 기록한다.
- 같은 접근으로 3회 연속 개선이 없으면 병목을 다시 확인하고 해당 접근을 종료하거나 다른 가설로 바꾼다.
- API 사용량·비용, 변환 시간, 측정 시간, 디스크 사용량을 실행마다 남긴다.
- 예산 소진 시 최선의 검증 후보와 미완료 항목을 보고한다. 예산 소진을 개선 성공으로 처리하지 않는다.

이 값은 초기 운영안이다. 착수 시 실제 비용·실행 시간을 확인하여 기록된 예산 안에서 진행한다.

## 6. 단계별 실험 설계

### 6.1 기준선과 비교 구성

| ID | 모델 양자화 | 엔진 | 설정 | 검증 목적 |
| --- | --- | --- | --- | --- |
| B0 | 배포 기준 M0 | 수정 없는 STRATA E0 | 기본 설정 | 사용자가 설치했을 때의 기준선 |
| B1 | M0 | E0 | 튜닝 설정 S1 | 설정 변경 효과 |
| Q1 | 맞춤 양자화 M1 | E0 | S1 | 양자화 변경 효과 |
| E1 | M0 | 수정 엔진 E1 | S1 | 엔진 변경 효과 |
| C1 | M1 | E1 | S1 | 두 변경의 결합 및 상호작용 |
| F1 | 최종 선택 모델 | 최종 선택 엔진 | 최종 설정 | 재시작·최종 품질·안정성 검증 |

B1·Q1·E1·C1은 같은 원본 모델 계열과 평가 조건을 사용한다. 엔진 수정이 M1 전용이면 E1 단독 결과를 억지로 만들지 않고 지원 불가 사유를 표시하며, 결합 효과의 귀속에 한계가 있음을 보고한다. C1 이후 설정을 다시 튜닝하면 별도 구성 ID를 부여한다.

### 6.2 실행 설정 탐색

선택한 리비전에서 실제 지원되는 항목만 탐색한다. 기존 llama.cpp의 옵션을 STRATA 옵션으로 그대로 대입하지 않는다.

- expert 캐시 크기·배치·적응 정책 및 cache hit/miss
- CPU 작업자 수·코어 배치, CPU 계산과 PCIe 전송의 분담
- prefill 청크·스테이징·버퍼 예산
- KV 저장 정밀도·배치·성장 정책
- MTP와 speculative decoding, draft 수·수락률
- 컨텍스트 4K·8K 진단 비교, 8K 완료 후 16K 확장

### 6.3 맞춤 양자화 탐색

1. 실제 텐서 형식 분포와 각 텐서의 메모리 비중을 추출한다.
2. 한국어·코딩 탐색 데이터로 민감도와 라우팅 특성을 측정한다.
3. 지원되는 단위에서 정밀도 배분·중요도 보정을 변경한다.
4. 파일 크기·관측 메모리·품질·전체 응답 시간을 함께 비교한다.
5. 최종 후보의 생성 레시피·원본 리비전·텐서별 타입 표를 저장한다.

고정밀 원본에서 후보를 생성하는 방식을 우선한다. 기존 저정밀 파일의 반복 재양자화는 손실을 추가할 수 있으므로 원본 복원으로 취급하지 않는다. 텐서 단위가 아닌 개별 expert 단위 정밀도 변경은 팩 레이아웃과 커널이 지원하는지 먼저 확인하며 기본 지원으로 가정하지 않는다.

고정밀 원본 전체가 RAM에 들어가지 않을 수 있다. 샤드·CPU·스트리밍 변환 가능성과 peak RAM·임시 디스크를 먼저 검증한다. 이 PC에서 변환이 불가능하면 그 사실을 기록하고 가능한 후보 범위만 수행한다. 임대 GPU나 업그레이드는 자동 전제로 추가하지 않는다.

### 6.4 엔진 코드 최적화

프로파일에서 시간 비중이 확인된 경로만 수정한다.

| 병목 후보 | 변경 예시 | 필수 검증 |
| --- | --- | --- |
| 전송·캐시 | expert 전송 중복 감소, 프리패치, 캐시 정책 | 라우팅·계산 대상 보존, 전체 지연 |
| CUDA 연산 | 디코딩·역양자화·행렬 연산 커널, 연산 결합 | 참조 출력 대비 수치 오차·범위 밖 접근 |
| 메모리 관리 | 버퍼 재사용, 할당·복사·동기화 감소 | 반복·긴 문맥·재시작 안정성 |
| CPU 경로 | 작업 분할·SIMD·스레드 운용 | 수치 정확성·CPU 시간·메모리 |

참조 구현과 bitwise 동일한 변경, 부동소수 반올림 수준의 변경, 계산 의미를 바꾸는 근사 변경을 구분한다. 허용 오차는 결과를 보기 전에 dtype·연산별로 정하고, 후보를 통과시키기 위해 사후 확대하지 않는다. 정확성 검사를 통과한 커널도 서버 전체 성능과 품질이 개선되어야 채택한다.

## 7. 측정 계획

### 7.1 지표

| 지표 | 정의·보고 방식 |
| --- | --- |
| PP | 엔진이 보고하는 실제 입력 토큰 처리량, 입력 길이별 분리 |
| TG | 엔진이 보고하는 실제 생성 토큰 처리량, reasoning 포함 여부 명시 |
| 첫 스트림 지연 | 첫 비어 있지 않은 reasoning 또는 content 수신까지의 시간 |
| 첫 답변 지연 | 첫 비어 있지 않은 최종 답변 content 수신까지의 시간 |
| 답변 완료 시간 | 요청부터 스트림 종료까지, 실제 출력 길이·완료 사유 동시 기록 |
| KV·expert 캐시 | 할당량·hit/miss·전송량·적응 상태 |
| 메모리 | 관측 Peak VRAM, 프로세스 작업 집합·프라이빗 메모리, 시스템 최소 가용 RAM |
| 하드웨어 상태 | GPU 사용률·온도·전력, CPU 부하, SSD·PCIe 사용 상태 |
| 품질·정확성 | 분야별 점수, 수치 오차, 오류·중단·OOM |

SSE 조각 수나 문자 수로 tok/s를 계산하지 않는다. MTP의 draft 토큰과 실제 채택 출력 토큰도 구분한다. reasoning을 먼저 보내는 모델에서는 두 종류의 첫 응답 지연을 분리하여 기록한다.

### 7.2 측정 조건

- 단일 사용자·동시 요청 1개, 목표 컨텍스트 8,192로 시작한다.
- 사용자 입력 512·2,048·4,096토큰 부근의 고정 문항과 출력 상한 128·512를 사용한다. 실제 템플릿 포함 토큰 수를 기록한다.
- 컨텍스트 한도에는 입력·특수 토큰·생성 예산을 함께 포함한다.
- thinking·샘플링·MTP·프롬프트 캐시 조건을 고정한다. 이를 변경하는 실험만 별도 구분한다.
- 모델 로딩·팩 생성·해시 계산 시간은 정상 응답 시간에서 분리한다.
- GPU 부하 프로그램을 정리하고 워밍업 후 측정한다. cold/warm 캐시 조건을 구분한다.
- 탐색은 설정당 3회 이상, 최종 후보는 5회 이상의 기준선/후보 교차 쌍으로 확인한다. 변동이 크면 반복을 늘린다.
- 중앙값·표준편차·반복 수를 보고한다. p95는 충분한 반복이 있는 최종 검증에서 보고하고, 소수 표본이면 탐색 수치로 표시한다.
- 500ms 간격 메모리 로그의 최대값은 관측 피크이며 실제 순간 최대치를 보장하지 않는다.

STRATA 표준 벤치마크는 호환 모델·버전에서 보조 사용한다. 확인한 공식 프로토콜은 draft 상태이며, 대상 프로필과 16K 입력 등 조건이 본 8K 실험과 다르다. 프로토콜을 임의 수정한 결과를 공식 준수 결과로 표시하지 않는다. [공식 벤치마크 프로토콜](https://github.com/Niko1221/Strata/blob/main/docs/BENCHMARK_PROTOCOL.md)

## 8. 품질 평가와 데이터 분리

### 8.1 데이터 용도

| 데이터 | 용도 | 에이전트 접근 |
| --- | --- | --- |
| 보정 데이터 | imatrix·민감도·라우팅 프로필 생성 | 가능 |
| 탐색 평가 세트 | 후보 선별·디버깅·반복 개선 | 가능 |
| 최종 평가 50문항 | 최종 품질 판정 | 후보 고정 후 별도 평가 절차로 실행 |

중복·유사 문항이 섞이지 않도록 출처와 버전을 기록한다. 최종 평가의 정답·채점기·문항별 결과는 최적화 작업 경로와 분리한다. 후보 선정 후 최종 평가 결과를 보고 추가 튜닝했다면 해당 세트는 더 이상 독립 평가로 간주하지 않고 새 보류 세트를 마련한다.

### 8.2 최종 평가 구성

| 분야 | 문항 수 | 평가 방식 |
| --- | --- | --- |
| 한국어 이해·요약 | 10 | 필수 정보 보존·사실 오류·지시 준수 |
| Python 코딩 | 10 | 고정 단위 테스트 통과 |
| SQL·데이터 처리 | 10 | 고정 데이터셋에서 정답 결과 일치 |
| 논리·수학 | 10 | 정답 및 요구 조건 충족 |
| 긴 문서 처리 | 10 | 근거 위치·답변 정확도 |
| 합계 | 50 | 전체·영역별 점수 병행 보고 |

KL divergence·perplexity·top-1 일치율은 후보 선별 보조 지표다. 이 지표 개선을 한국어·코딩 정답률 개선이나 속도 향상으로 대체 해석하지 않는다. 고정밀 또는 Q8 참조 실행이 자원상 불가능하면 사용한 대체 참조와 한계를 명시한다.

## 9. 최종 채택 기준

1. 목표 모델·8K·단일 요청에서 정상 실행되고 OOM·응답 오류가 없어야 한다.
2. 최종 50문항의 전체 및 각 영역 점수가 기준선보다 낮아지지 않아야 한다. 표본의 한계와 확률적 출력 변동은 재평가로 확인한다.
3. 엔진 패치는 사전 정의한 수치 정확성 검사와 해당 경로의 회귀 검사를 통과해야 한다.
4. 같은 PC에서 교차 측정했을 때 응답 시간·처리량·메모리 중 목표 지표의 이득이 반복적으로 관찰되어야 한다.
5. 속도 향상은 기준선 자체 변동폭과 함께 판단한다. 근거가 약하면 개선 미확인으로 기록한다.
6. 최종 상태로 서버 재시작 후 재현하고, 혼합 요청 50회와 60분 사용 시험을 모두 수행해 오류와 메모리 증가를 점검한다.

답변을 짧게 만들거나 reasoning을 끄는 변경은 토큰 처리량 개선과 구분한다. 낮은 비트 수로 모델이 작아져도 실제 엔진이 느려질 수 있으므로 메모리·속도·품질을 각각 보고한다. 안정성과 품질을 만족하는 후보들 중 목표 사용에 적합한 구성을 선정한다.

## 10. 일정 및 단계별 완료 조건

아래는 1인과 AI 에이전트 기준의 7~10 작업일 초기안이다. 변환 자원·빌드 난이도·API 예산에 따라 조정하며 엔진 수정 성공을 일정으로 보장하지 않는다.

| 단계 | 예상 배정 | 완료 조건 |
| --- | --- | --- |
| 호환성·자원 조사 | 1일 | 엔진·모델 지원, 메모리·디스크·CPU·PCIe 정보 확보 |
| 환경 및 기준선 | 1~2일 | M0·E0 고정, B0 성능·품질·자원 로그 확보 |
| 실행 설정 튜닝 | 1일 | B1 결과, 병목 프로파일, 후보 순위 |
| 맞춤 양자화 | 1~2일 | M1 레시피·형식 표·호환성·품질·Q1 결과 |
| 엔진 최적화 | 2~3일 | 패치·검사 결과·E1 및 결합 비교 |
| 최종 검증·정리 | 1일 | 독립 품질 평가, 안정성 시험, 재현 묶음 |

양자화 생성이 자원상 불가능하거나 엔진 수정에서 이득이 없으면 미달 항목으로 표시한다. 기준선과 튜닝 결과를 전달할 수는 있지만 양자화·엔진 최적화까지 완료했다고 표현하지 않는다.

## 11. 자원·변경·비용 관리

- 원본 모델, 수정 없는 엔진, 원시 측정 결과는 덮어쓰지 않는다.
- 모델 리비전·파일 SHA256, 팩 생성 명령·인덱스·해시, 엔진 커밋·빌드 옵션을 연결한다.
- 각 패치는 분리된 브랜치나 체크아웃에서 관리하고 검증 후보만 운영 경로에 반영한다.
- 실패 모델·패치는 실행 구성에서 제외하고 복원 가능하게 기록한다. 대용량 중간 파일 정리 시 최종 후보와 재생성 레시피를 보존한다.
- 다운로드·고정밀 원본·중간 GGUF·팩·빌드·로그가 동시에 차지할 공간을 사전 계산한다.
- CUDA 지원 Windows C++ 도구 체인과 필요 시 프로파일러를 확인한다. 프로파일러가 없으면 엔진 계측으로 시작한다.
- 외부 에이전트에는 공개·합성 평가 데이터를 우선 사용하고, 개인 코드·문서·가중치 전체가 도구 사용 과정에서 전송되는 범위를 확인한다.
- 최적화 호출 비용과 실제 실행 시간은 성능 이득과 함께 보고한다. 필요한 구독·API 사용 권한과 예산을 착수 시 확정한다.
