## 3. 해석

- **클라우드 토큰은 거의 같다.** 지배적인 값은 캐시 읽기(티켓당 약 28만)로, API 요청 한 번마다 그때까지의 대화 전체(약 13~15만)를 다시 읽는 비용이다. 그래서 클라우드 비용은 "무엇을 쓰느냐"보다 **요청 횟수**가 정한다. 이번에는 두 방식 모두 티켓당 2번이었다(위임 = 위임 호출 → 반영 · 확인, 직접 = 읽기 → 편집 · 확인).
- **짧은 명세 티켓은 직접 편집과 출력이 같았다**(1,094 vs 1,064). 이 작업은 직접 해도 편집 지시가 짧다(줄 번호 몇 개, 교체 문자열 몇 줄). 티켓을 짧게 써도 아낄 출력이 처음부터 적었다.
- **위임은 캐시 쓰기가 1.8배.** 워커 응답(diff · 요약 · 통계 JSON, 티켓당 약 1.4K 토큰 더)이 대화에 붙기 때문. 이 차이는 다음 요청부터 캐시 읽기에도 계속 남는다.
- **시간은 직접이 2.8배 빠르다.** 워커가 티켓당 42초(모델 호출 4.3번, 매번 처음부터 읽음 — T-013)를 쓰는 동안 지휘자는 기다렸다. 이번에는 기다리는 동안 다른 일을 하지 않았다(측정을 깨끗이 하려고 순서대로 돌림).
- 로컬은 티켓당 입력 약 1.7만 · 출력 약 1.8천 토큰으로 몇 줄짜리 편집을 했다. 무료이고 클라우드 한도를 쓰지 않는다.
- **지난 시연과 비교**: 추정은 위임 약 7천 vs 직접 약 4~6천(요청 5건 묶음)이었다. 이번 실측으로 캐시 읽기를 빼고 보면 티켓당 위임 4.2천 vs 직접 2.7천 — **방향이 같다(위임이 약간 더 든다)**. 티켓을 코드 수준에서 짧은 명세로 바꿔도 이 결론은 바뀌지 않았다. 티켓 작성 비용보다 요청 횟수와 워커 응답 크기가 더 컸다.
- 결론: **기계적인 몇 줄 편집은 짧은 명세로 맡겨도 클라우드 토큰이 줄지 않고(약 +6%), 시간은 늘어난다.** 위임이 클라우드를 아끼려면 직접 할 때 **요청 횟수가 많아지는 일**이어야 한다 — 여러 파일을 찾아 읽거나, 테스트를 돌리며 몇 번 고쳐야 하는 일. 그런 일은 지휘자 대화 전체를 매번 다시 읽는 비용을 워커가 대신 진다.

## 4. 한계

- **같은 작업의 A/B 가 아니다.** 짝은 같은 범주 · 비슷한 곳 수의 서로 다른 파일이다. 표본 6쌍.
- 직접 쪽은 편집 스크립트(`ed_a.py` 줄 번호 지정, `ed_b.py` 정확 교체 JSON)를 한 번 써 두고 재사용했다. 처음 쓴 비용은 2번 · 7번 티켓에 들어 있다. 위임 쪽은 1번 티켓에 반영 스크립트(`apply_chk.cmd`)의 cmd 오류를 고친 요청 2번이 들어 있다(C-043). 둘 다 그 티켓 안에 그대로 두었다.
- 검사 스크립트 `chk_pat.py` · 반영 스크립트는 첫 티켓 전에 썼다(티켓 밖, 두 방식이 같이 씀).
- 지휘자가 여러 도구 호출을 한 요청에 묶었다. 요청 횟수가 비용을 정하므로 묶는 습관이 결과에 크게 작용한다.
- 문맥 크기가 티켓마다 커진다(13만 → 15만대). 순서를 번갈아(L C C L L C C L L C C L) 같은 방향으로 치우치지 않게 했지만 완전히 상쇄되지는 않는다.
- 티켓 중간에 앱이 보낸 "진행 상황을 말하라" 알림에 답한 짧은 문장이 몇 티켓에 섞여 있다(두 방식 모두).
- 시간은 도구 실행 시각으로 잰다. 메시지 사이 간격(티켓 사이 0~13초)은 어느 티켓에도 넣지 않았다(구간 밖 4 요청).
