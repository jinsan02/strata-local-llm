# 읽기 요약 · 배치 위임: 클라우드 지휘자 토큰 실측 (11-26)

[직전 실측](usage-measure-20261126.md)의 결론은 "클라우드 비용은 **요청 횟수 × 대화 크기**가 정한다. 몇 줄 편집은 짧은 명세로 맡겨도 +6%, 시간 2.8배"였다. 이번에는 그 결론을 직접 시험하는 두 사용법을 쟀다.

- **실험 1 읽기 요약**: 많이 읽고 짧게 답하는 질문을 로컬 워커에 맡기면(L) 지휘자가 읽을 양이 줄어 싸지는가. 직접(C)과 짝 6쌍
- **실험 2 배치 위임**: 정리 티켓 6개를 한 번에 맡기고 한 번에 검토하면(배치) 요청 횟수가 줄어 싸지는가. 직접 6개와 비교

환경은 직전과 같다. 지휘자 Claude Code(노트북, Opus 5.5, 새 세션), 워커 `delegate_code_task` → 본체 STRATA(M0 · E2 · 64K · high · H12, 서버 127.0.0.1). 브랜치 `exp/read-batch-20261126`.

## 0. 방법

- **구간**: 첫 요청에 `date` 를 같이 보내 시작, 마지막 요청(답 기록 · 확인 통과)에 `date` 를 같이 보내 끝. 클라우드 토큰은 이 세션 transcript 의 assistant `usage` 를 message id 로 한 번씩 세어, 시작 `date` 가 든 메시지부터 끝 `date` 가 든 메시지까지 더했다(transcript 시각이 내용 블록마다 찍혀 초 단위 경계가 어긋나므로 메시지 단위로 자름). 집계 스크립트는 세션 scratchpad(저장소에 넣지 않음)
- **단가 비율 환산**(참고값): 입력 1 · 캐시 쓰기(1시간) 2 · 캐시 읽기 0.1 · 출력 5 → "입력 토큰 상당". 플랜 한도가 실제로 어떻게 세는지는 모른다
- **도구 호출 묶기**: 두 방식 모두 "읽기(보통 1요청) + 답 기록 · 확인 1요청"으로 같게 했다. 직접 쪽은 지휘자가 평소처럼 `git grep` · 짧은 Python 으로 답을 뽑았다(파일 전체를 대화에 읽어 들이지 않음)
- **측정 밖**: 배치 실행기 `scripts/worker/batch.py` 작성 · 시범(b1e1b38), 질문 · 티켓 고정, 직접 쪽 확인 스크립트 `work/stage/chk2.cmd`, 정답 생성, 집계. 읽기 전용 위임 형식 시범 1회(상태 `no_change`, 답은 `summary` 로 옴 — 확인)
- 플랜 사용량(측정 시작 직전 → 집계 직후, 채점 · 집계 포함): 5시간 한도 45% → 52%, 주간 24% → 25%. 문맥 137K → 203K

## 3. 해석 · 직전 실측과 비교

| 사용법 | 클라우드 환산(위임 ÷ 직접) | 시간 | 정확도 · 결과 |
| --- | --- | --- | --- |
| 짧은 명세 위임 1티켓씩 (직전) | 1.06 (+6%) | 2.8배 | 6/6 done |
| 읽기 요약 1질문씩 (실험 1) | 1.34 (+34%), 실패 1건 빼면 1.09 | 11배 | 맞음 4 · 부분 1 · 틀림 1 (직접 6/6) |
| 배치 6티켓 한 번에 (실험 2) | **0.55 (−45%)**, 버그 빼면 약 0.34 | 3.8배(대기 포함) | 직접과 같음 |

- **결론을 확인했다: 비용은 요청 횟수가 정한다.** 요청 하나가 그때 대화 전체(이번 15~18만 토큰)를 캐시로 다시 읽으니, 환산값의 약 80%가 캐시 읽기다. 배치는 요청을 13 → 6(버그 없으면 4)으로 줄여 캐시 읽기가 0.48배가 됐고, 그만큼 싸졌다. 캐시 읽기를 뺀 나머지(입력 · 캐시 쓰기 · 출력)는 0.95배로 거의 같다 — 배치는 '덜 쓰기'가 아니라 '덜 묻기'로 아낀다.
- **읽기 요약은 아끼지 못했다.** 지휘자는 많이 읽어야 하는 질문도 `git grep` · 짧은 Python 으로 답을 뽑아 2요청에 끝냈고, 대화에 들어온 도구 출력도 작았다(캐시 쓰기 평균 1.5K). 워커 응답(JSON · 경고 · handoff 문구, 약 1~1.5K 토큰)이 그보다 커서 캐시 쓰기가 2배였다. 요청 수가 같으면 아낄 곳이 없다. 게다가 로컬 답 6개 중 2개가 틀리거나 부분이었고, 틀린 1건은 재시도 · 직접 처리로 요청이 5번이 됐다.
- 읽기 요약이 이득일 수 있는 곳은 **스크립트로 못 뽑고 지휘자가 실제로 본문을 여러 번 읽어야 하는 질문**이다. 8번에서 워커는 목록 표에 없는 T-027 · T-028 을 본문에서 찾았다 — 지휘자가 같은 답을 얻으려면 본문을 읽느라 요청이 늘었을 것이다. 이번 질문 세트에는 그런 질문이 적었다(이번 설계의 한계).
- **배치의 대가는 시간과 검토 부담**이다. 지휘자 쪽 요청은 줄었지만 끝까지 약 4.6분(직접 1.2분)이 걸렸다. 기다리는 동안 지휘자가 다른 일을 하지 않아야 아낀다(다른 요청을 보내면 그 요청도 대화 전체를 다시 읽는다 — 다른 일이 이 작업과 상관없는 일이라면 어차피 드는 비용이다).
- 직전 실측과 같은 방향이다. 1티켓 1위임은 요청 수가 직접과 같아(2 vs 2) 이득이 없었고, 배치는 요청 수를 티켓당 1 미만으로 낮춰 이득이 났다.
- **쓸 만한가**: 배치는 **쓸 만하다** — 서로 독립인 기계적 티켓을 확인 명령과 함께 여러 개 모아 한 번에 맡기고, 끝 알림 뒤 한두 요청으로 검토 · 반영한다. 읽기 요약은 **지금 형태로는 쓰지 않는다** — 스크립트로 답이 나오는 질문은 지휘자가 직접 하는 편이 싸고 정확하다.
