# L2 관찰 마스킹 vs 64K (11-21, STATE 25-4)

목표: 남은 실패(metadata_extra_dupes 0/5 · specifier_bounds 0/5, H7 기준)를 줄인다. 같은 과제로 '오래된 도구 출력 지우기(32K)'와 '64K'를 비교해, 24번의 64K 결정에도 같이 쓴다.

## 1. 실패가 왜 나는가 (x3h7 · x3s1c 도구 기록, 서버 없이)

두 과제의 실패 20회(H7 10 · 대조 10)는 **모두 도구 편집이 0회**다. 강제 마지막 턴까지 가서 텍스트 블록 하나로 답했다.

| 과제 | 큰 파일 | 읽는 방식 | 읽은 양 | 강제 턴 직전 입력 |
|---|---|---|---:|---:|
| specifier_bounds | specifiers.py 약 1,400줄 | 처음부터 12,000자씩 5~6번 넘겨 읽음 | 73~105K자 | 21.8~25.3K |
| metadata_extra_dupes | metadata.py 약 1,060줄 | 처음부터 4~5번 넘겨 읽고 markers.py · _parser.py 도 통째 | 76~102K자 | 21.8~25.8K |

- 통과하는 과제(dg · marker · version · tags)도 입력은 2.2만 근처까지 가지만, 그 전에 edit_file 로 고친다(첫 편집이 3~10번째 호출).
- 이 두 과제는 '다 읽고 나서 고치기'를 하다가 고칠 차례에 문맥이 끝난다. 앞에서 읽은 파일 조각은 다시 볼 일이 적은데 계속 입력에 남아 있다.

## 2. 두 팔

| 팔 | 접두사 | ctx | 바뀌는 것 | 손실 |
|---|---|---|---|---|
| 대조 | x3h7 | 32K | (17/30, 다시 안 돌림) | — |
| A: L2 마스킹 | x3l2 | 32K | 입력 > 16,000 이면 그때 한 번에, 최근 도구 결과 2개를 빼고 오래된 큰 결과(400자 이상, edit_file 제외)를 자리표시로 바꿈. 입력 ≤ 10,000 이 될 때까지만, 다시 넘으면 또 | 가능(다시 읽으면 복구) |
| B: 64K | x3k64h7 | 64K | 강제 턴 문턱 55,296 (ctx − 8,192 − 2,048). 나머지 같음 | 없음(대신 RAM · 속도) |

- 공통: M0 · H0 + `--edit-apply lenient` + card-coding · seed 42~46, 6과제 x 5회.
- 자리표시: `(문맥 절약: 이 도구 결과(read_file src/packaging/specifiers.py 줄 300~끝, 12000자)는 지웠다. 필요하면 다시 호출하라.)`
- 모델의 말 · 도구 호출 인자 · edit_file 결과는 지우지 않는다. 지운 위치는 하네스만 들고 있고 서버로 가는 메시지에는 다른 키를 넣지 않는다.
- 매 턴 지우지 않고 문턱에서 몰아서 지운다(loop-plan 5절: OpenHands 관찰 마스킹 · Claude Code · Codex 의 '한 번에, 늦게'). 하이브리드 모델은 앞부분이 바뀌면 전체를 다시 처리하므로, 마스킹 1번 = 재처리 1번(PP 약 1,500 tok/s → 10초 안팎).
- 실행마다 `mask_r{i}.json`(턴 · 전후 입력 · 지운 수 · 글자 수), 원장 note 에 `masks · masked_outputs · masked_chars`.
- 자체 점검 `scripts/bench/selftest_mask.py` 10항목(가짜 모델 · 가짜 토큰 수로 off/on 비교 포함).
- 체인: `scripts/bench/l2-chain.ps1` = g3-chain 을 A(32K, -Mask) → B(64K) 순서로 두 번. g3-chain 은 이제 `--ctx` 를 run_x3 에 넘긴다.

## 3. 판정

- 각 팔: 16 이상(대조 17 의 −1 이내)이면 해가 없음, 18 이상이면 효과. 짝 · 숨은 테스트 합 · 강제 턴 수 · 도구 편집이 있는 실행 수를 같이 본다.
- A 는 손실 가능한 변경이라 −1 이내를 엄격히 본다. metadata · specifier 가 오르는데 다른 과제가 떨어지면(지운 내용을 다시 못 찾음) 채택하지 않는다.
- 둘 다 효과가 비슷하면 A(32K + 마스킹)를 고른다: RAM 여유 · 속도 · 지금까지의 32K 측정을 그대로 쓸 수 있다.
- B 의 결과는 24번 64K 결정에 그대로 쓴다(다시 재지 않는다).

## 5. 결과 B: 64K (11-21 21:31 ~ 11-22 01:56, `x3k64h7`) → 효과

| | H7 대조 (x3h7, 32K) | B: 64K |
|---|---:|---:|
| 통과 | 17/30 | **21/30** |
| 짝 (B 만 통과 : 대조만 통과) | | 6 : 2 |
| 숨은 테스트 합 / 550 | 361 | **510** |
| 실패 유형 | test_fail 8 · import_or_syntax 5 | test_fail 9 · import_or_syntax 0 |
| 회차당 시간 | 약 24분 | 약 53분 (44~62분) |
| 마지막 입력 최대 | 문턱 22,272 근처 | 39,315 (문턱 55,296 에 안 닿음) |

| 과제 (r1~r5) | H7 | B |
|---|---|---|
| dg_group_names | 11111 | 11111 |
| marker_extras | 11010 | 10111 |
| version_bump | 11111 | 10111 |
| tags_platform_filter | 11011 | 11111 |
| metadata_extra_dupes | 00000 | 00000 (숨은 19 · 15 · 15 · 15 · 15 / 20) |
| specifier_bounds | 00000 | **10110** (숨은 30 · 19 · 30 · 30 · 28 / 30) |

- specifier 가 M0 에서 처음 통과했다(3/5). 큰 파일을 다 읽고도 문맥이 남아 편집까지 간다.
- metadata 는 5회 중 4회가 숨은 15/20 에서 멈춘다. 같은 하위 사례를 놓치는 것으로 보이며 문맥 문제가 아니다(도구 기록 확인은 남은 일).
- 어려운 두 과제는 호출 17~19번에서 끝난다. 64K 에서 막는 것은 `max_steps` 20 이지 문맥이 아니다 → 노력치 xhigh(호출 상한 30) 후보.
- r2 의 version · marker 실패는 쉬운 과제의 잡음 범위(대조에도 같은 크기의 흔들림)로 본다.
- 시간은 같은 입력 길이에서 3~8% 느릴 뿐이고, 더 많이 읽고(입력 32~39K) 더 오래 생각해서(think 약 2.5배) 늘어난다.
- RAM: 측정 중 여유 약 0.5GB, 끝난 뒤 26.7GB 회복. OOM · 서버 오류 없음.
- 판정: 18 이상 → 효과. A 는 기각이라 "둘 다 비슷하면 A" 규칙은 해당 없다. **24번 결정: 64K 를 노력치 high 로 쓴다.** 기본(medium)은 32K 와 같은 문턱을 64K 서버에서 쓰고, 같은지 한 번 확인한다(STATE 26).
