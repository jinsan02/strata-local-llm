# 함께 삽질 기록 (사람 + AI 조수)

`TROUBLESHOOTING.md` 는 시스템 문제를 적는다. 여기는 **사람과 AI 조수(Claude Code)가 같이 일하면서 생긴 헛수고 · 착각 · 소통 문제**를 적는다.
나중에 블로그(velog)에 쓸 재료. 항목마다: 상황 → 무엇이 틀렸나 → 어떻게 알아챘나 → 교훈. 숫자와 커밋은 사실 그대로.

태그: `가설` 잘못된 가설 · `도구` 셸 · 인코딩 · 경로 · `소통` 말이 어긋남 · `통계` 숫자 해석 · `운영` 원격 · 무인 실행 · `절차` 규칙 · 커밋

## C-039 대조 한 묶음만 보고 "E3 에서만 나온 패턴" 이라고 보고

- **상황**: E3 X3 미달을 조사하며 편집 성공 방법에 `indent-2` 8건이 있고 대조 x3h9 에는 0건인 것을 보고 "E3 가 문맥을 미세하게 바꾼다" 는 가설과 함께 사용자에게 보고했다.
- **무엇이 틀렸나**: 전 기록을 세니 indent-2 는 62건(y9 8 · x3exh 9 · x3h9t 5 …)으로 모델의 오래된 습관이었다. x3h9 가 우연히 0. 같은 날 V2 를 '30분이면 증명' 이라고 제안했지만 엔진 자체가 greedy 에서도 비결정적이라 증명이 안 됐다(T-028) — 잡음 바닥을 먼저 재지 않았다.
- **어떻게 알아챘나**: 사용자가 조사를 맡겨 전 이력을 센 직후, V2 의 E2 대 E2 비교에서.
- **교훈**: 새 패턴을 조건 탓으로 돌리기 전에 전 이력에서 빈도부터 센다. 재현 비교를 근거로 삼기 전에 같은 조건 두 번의 차이를 먼저 잰다.

## C-038 조사 보고에서 'git 훅이 없다' 고 말함 → 실제로 `.githooks` 가 이미 있었다

- **상황**: 하네스 엔지니어링 조사 보고에서 '커밋 규칙 · 비밀값 · 금지 경로가 글로만 있으니 git 훅으로' 를 2순위로 제안했다.
- **무엇이 틀렸나**: 저장소에 `.githooks/commit-msg`(제목 72자 · record 트레일러를 원장과 대조 · fix 의 Invalidates)와 `pre-commit`(final_eval · engine · data · 모델 바이너리 경로)이 이미 있고 `core.hooksPath` 로 켜져 있었다. 실제로 빠진 것은 비밀값(키 값) · 한국어 .ps1 BOM 검사 정도였다.
- **어떻게 알아챘나**: 기록 정리 중 TROUBLESHOOTING 의 T-018 '커밋 훅' 을 보고 확인했다.
- **교훈**: '우리에게 없다' 는 주장은 저장소를 먼저 찾아본 뒤에 한다. 외부 비교 문서는 우리 상태 열을 실제 파일로 채운다.

## C-037 같은 날 문자열 층 실수 다섯 번

- **상황**: 본체 로컬 환경 스크립트와 재현 스크립트를 쓰며 하루에 다섯 번 문자열 층에서 틀렸다.
- **무엇이 틀렸나**: (1) `strata-status.ps1` 에서 주소가 하나면 파이프 결과가 스칼라라 `$addr[0]` 이 첫 글자 '1' (2) bash heredoc · sed 를 거친 Python 경로 리터럴의 백슬래시가 두 번 사라짐 (3) CRLF 파일에 `\n` 정규식을 걸어 assert 실패 (4) perl 치환이 맞지 않아 그대로 남음 (5) `claude-desk` 인자 묶임(T-026).
- **어떻게 알아챘나**: 모두 바로 다음 실행 결과(응답 실패 · SyntaxError · assert · 출력 확인)로. 사고로 번진 것은 없다.
- **교훈**: 파이프 결과는 `@()` 로 감싼다. 원격에서 돌릴 Python 의 경로는 `/` 로 쓴다. 파일을 고칠 때는 줄 끝을 먼저 본다. 여러 층을 거치는 치환은 Edit 도구로. 체크리스트 메모리에 두 항목 추가.

## C-036 허용 목록에 `python -c` 를 넣었더니 모델이 GitHub 원본을 받아 옴

- **상황**: X4b(본체 · 테스트 실행 허용) 일괄에서 Bash 허용 목록을 `python -m pytest` · `python -c` · `git diff/status` 로 잡았다. dg r2 가 `git clone` · `curl` 이 막히자 `python -c` 로 urllib 다운로드를 했다(T-025).
- **무엇이 틀렸나**: `python -c` 는 임의 코드 실행이라 허용 목록의 의미가 없었다. audit 는 '저장소 밖 금지 경로' 만 보도록 만들어 네트워크를 놓쳤다. 사람 승인이 필요한 다운로드가 모델 손으로 일어났다.
- **어떻게 알아챘나**: 진행 확인 중 diff 1.9MB(평소 수 KB)가 눈에 띄어 기록을 열었다.
- **교훈**: 허용 목록은 '무엇을 할 수 있게 되는가' 로 따진다. 범용 인터프리터는 빼고, 네트워크는 환경에서 막고, 기록 검사는 막은 것을 다시 확인하는 2차 장치로 둔다.

## C-035 X4 A 4/16 을 모델 탓으로 볼 뻔: 모델에게 간 도구가 Read · Edit 둘뿐

- **상황**: 노트북 Claude Code 로 16건 중 4건 통과. 하네스(같은 과제 약 14/16)보다 크게 낮아 '실제 클라이언트에서는 모델이 약하다' 로 정리할 뻔했다.
- **무엇이 틀렸나**: stream-json init 줄의 도구 목록이 `["Edit","Read"]` 였다. `CLAUDE_CODE_SIMPLE` 이 도구를 줄이고 X4 가 Bash 를 막아 파일 목록을 볼 수단이 없었다(T-021).
- **어떻게 알아챘나**: 도구 오류를 모아 보니 'File does not exist' 가 122번 — 경로 추측이 주된 행동이었다.
- **교훈**: 클라이언트 비교는 '모델이 실제로 받은 것'(도구 목록 · 프롬프트 크기)부터 확인한다. stream-json 기록으로 바꿔 둔 덕에 원인을 찾았다.

  H0 자체도 날마다 44~67% 로 출렁였는데, 그걸 '하락' 으로 해석할 뻔했다.
- 알아챈 계기: 사용자의 "되돌아보면 빠뜨린 게 있나?" 질문에 답하면서 처음으로 분산을 계산.
- 교훈: 기준을 '엄격하게' 만들기 전에 그 기준이 잡음보다 넓은지부터 본다. 대책: 과제 확대 · 짝 비교 순차 검정 · '유의하게 나쁘지 않음'.
  파인튜닝을 안 해도 '여러 후보 중 고르기' 자체가 튜닝이라 승자의 저주가 생긴다.

## C-015 "샘플링이 무작위다" 라고 말했다가 코드를 읽고 정정
- 상황: 되돌아보기에서 "run_x3 · 서버에 temperature · seed 지정이 없어 엔진 기본값으로 돈다" 고 보고.
- 틀린 것: run_x3 파일만 grep 했다. 실제 값은 import 한 run_bench.SAMPLING 에 seed 42 까지 명시돼 있었다.
- 알아챈 계기: 사용자가 "옵션 다 제대로 봐줘" 해서 서버 · 엔진 · 클라이언트를 끝까지 따라감.
- 교훈: '없다' 는 주장은 import 경로까지 확인한 뒤에. 그리고 오히려 더 중요한 사실이 나왔다 — seed 가 고정인데도 결과가 다르다
  = 잡음은 수치 비결정성(하이브리드 CPU/GPU expert 등)에서 온다. 정정은 바로, 숨기지 않고.

## C-014 15:00 중간 점검을 약속하고 15:23 에 사용자가 먼저 물음
- 상황: "80분 뒤 깨워서 중간 점검" 을 노트북 쪽 백그라운드 sleep 으로 걸어 둠.
- 틀린 것: 노트북이 잠들면 sleep 도 멈춘다. 측정은 본체에서 멀쩡히 돌았지만 보고가 늦음. 사용자는 시간대가 다른 줄 알았다
  ("서울 시각으로 맞춰서 하자") — 실제로는 두 PC 모두 KST 였고 단순히 늦은 것.
- 교훈: 보고 약속은 '내 감시가 깨어 있다' 는 전제 위에 있다. 깨어 있기 요청 + 늦으면 원인을 먼저 말한다(시간대 탓 아님).

## C-013 Codex 참고 측정이 전부 0점 → 채점 환경 실수
- 상황: 같은 과제(D · E · F)를 Codex 두 모델에 시키고 비공개 테스트로 채점.
- 틀린 것: 첫 채점 결과가 두 모델 모두 기본 코드 점수와 똑같고 회귀까지 실패. 채점 때 `PYTHONPATH=src` 를 안 줘서 설치된 packaging 을 시험했다.
- 알아챈 계기: '두 모델 숫자가 완전히 같다' + '기본 코드 점수와 같다' 가 이상해서 run_x3 의 채점 함수와 비교.
- 교훈: 너무 깔끔하게 같은 숫자는 버그 냄새. 채점은 검증된 함수 하나만 쓴다(T-017). 다시 채점하니 두 모델 모두 3/3.

## C-012 9회 표본의 8/9 를 믿었다가 30회 확인에서 뒤집힘
- 상황: H1(페이지 나누기)이 X3 8/9 로 '가장 정확' 해 보였다. 그래서 H1 + H2a = H3 를 만들었다.
- 틀린 것: 9회로는 거의 정보가 없다. H3 는 3/9 → 30회에서 12/30.
- 교훈: 작은 표본의 1등은 운일 확률이 높다. 오늘 밤 H1 단독 30회 재확인.

## C-011 채택 후보 H3 를 확인 체인이 기각 (-5)
- 상황: H3 는 시간 -30%, 새로 읽은 입력 -82% 로 효율이 압도적. 15회 탐색에서 '품질 같음'.

- 교훈: 효율이 좋으면 정확도 차이를 잡음으로 보고 싶어진다. 사용자가 미리 '정확도 우선' 을 정해 둔 덕에 고민 없이 기각.

## C-010 측정 체인이 도는 중에 추적 경로에 파일을 만들 뻔
- 상황: H4 체인이 도는 중에 새 과제 D · E · F 파일을 configs/ 에 만들었다.
- 위험: 원장 행마다 git_dirty 를 기록 — 체인 중 추적 경로가 바뀌면 그 뒤 행이 전부 '더러운 코드' 로 기록된다.
- 조치: 2분 안에 work/(git 무시) 로 옮김, 영향 행 0. 이후 규칙: 측정 중 준비물은 work/stage 에서만, 반영은 체인 뒤 스크립트로.

## C-009 대화 캐시 옵션이 문제를 풀 거라는 가설 → 엔진 경로에 없는 옵션
- 상황: 후속 턴에서 캐시 재사용이 0 (T-013). `--conversation-cache-mib` 크기를 바꾸는 A/B 를 설계 · 실행.
- 틀린 것: 세 조건 결과가 똑같음. 엔진 소스를 보니 q36 경로는 그 옵션을 아예 안 쓰고, '들고 있는 토큰 전체가 새 프롬프트의 앞부분일 때만' 재사용.
- 교훈: 옵션 A/B 전에 그 옵션이 실제 코드 경로에 닿는지부터 grep. 대신 원인은 확정됐고(reasoning 을 다시 보내면 해결 = H2a) 엔진 개선 후보(E1)가 생김.

## C-008 커밋 훅에 두 번 막힘
- 프로젝트 커밋 규칙을 훅이 검사한다. (1) record 커밋: 트레일러(Run-Id · Ledger · Config-SHA256)와 Co-Authored-By 사이에 빈 줄 → 거부.
  (2) env 커밋: 제목 다음 줄에 바로 트레일러(본문 없음) → "제목과 본문 사이 빈 줄" 거부.
- 교훈: 규칙을 사람이 만들고 훅이 지키게 하면, AI 조수도 같은 규칙에 막힌다 — 좋은 일. 메시지는 파일로 쓰고 -F 로.

## C-007 셸 안의 셸 안의 문자열: 백슬래시가 사라짐
- 구조: 노트북 bash → ssh → Windows cmd → powershell -Command → 안에 Python · 경로 문자열.
- 사례: heredoc 안 Python 의 `\U` 경로, sed 로 고친 PowerShell 줄에서 `$b\h1conf` 의 백슬래시가 빠져 `$bh1conf`, sed 구분자 `#` 충돌.
- 교훈: 두 겹 넘는 따옴표는 하지 않는다. 파일로 써서 scp → 원격에서 실행. 고친 뒤에는 반드시 해당 줄을 다시 출력해서 눈으로 확인 + 파서로 문법 검사.

## C-006 노트북 재부팅 → 감시 프로세스 사망, Tailscale 늦게 붙음, 원격 데스크톱은 원래 불가
