## 2. 읽는 법 · 한계

- **티켓이 아주 구체적이었다.** 함수 이름 · 인자 · 경계 조건 · 넣을 위치까지 적었고, 테스트를 먼저 줬다. done 5/5 는 "이 정도로 쪼개 주면 된다"는 뜻이지, 워커가 모호한 요청을 처리한다는 뜻은 아니다.
- 그래서 **지휘자 일이 줄었다기보다 바뀌었다.** 지휘자는 쪼개기 · 테스트 · 명세 · diff 검토 · 동작 대조를 했고, 워커는 기계적인 편집을 했다. 클라우드 토큰을 "지휘자 혼자 했을 때"와 비교하는 값은 재지 않았다(같은 요청 A/B 를 하지 않으므로).
- 5건 · 6티켓은 작다. 통과율로 일반화하지 않는다. F1(68/90)이 더 넓은 근거다.
- 위임 전 확인이 제 역할을 한 예: R3 를 기계적으로 거절했고, 지휘자 판단(측정 하네스 핵심, 원장 행 형식 결정)과도 맞았다.

## 4. 결론

- 워커 주 경로(지휘자가 쪼개고, 테스트를 먼저 주고, 파일 1~2개 티켓으로)는 이번 실사용에서 그대로 통했다.
- 맡기지 않는 기준(큰 파일 · 테스트 작성 · 문서 판단)도 그대로 유지한다. 바꿀 근거가 없었다.
