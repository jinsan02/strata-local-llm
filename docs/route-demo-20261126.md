## 2. 읽는 법 · 한계

- **티켓이 아주 구체적이었다.** 함수 이름 · 인자 · 경계 조건 · 넣을 위치까지 적었고, 테스트를 먼저 줬다. done 5/5 는 "이 정도로 쪼개 주면 된다"는 뜻이지, 워커가 모호한 요청을 처리한다는 뜻은 아니다.
- 그래서 **지휘자 일이 줄었다기보다 바뀌었다.** 지휘자는 쪼개기 · 테스트 · 명세 · diff 검토 · 동작 대조를 했고, 워커는 기계적인 편집을 했다. 클라우드 토큰을 "지휘자 혼자 했을 때"와 비교하는 값은 재지 않았다(같은 요청 A/B 를 하지 않으므로).
- 5건 · 6티켓은 작다. 통과율로 일반화하지 않는다. F1(68/90)이 더 넓은 근거다.
- 위임 전 확인이 제 역할을 한 예: R3 를 기계적으로 거절했고, 지휘자 판단(측정 하네스 핵심, 원장 행 형식 결정)과도 맞았다.

## 4. 토큰: 로컬 워커 vs 클라우드 지휘자 (사용자 요청, 11-26)

로컬은 워커 기록(`work/worker/logs/<id>.json` 의 turns)에서 합산한 **실측**이다. 클라우드는 세션 토큰을 단계별로 나눠 볼 수 없어 글자 수로 환산한 **추정**이다(코드 · 영문 약 3.5자 = 1토큰, 한글 1음절 ≈ 1토큰).

| 로컬 워커 (실측, 티켓 5개) | 값 |
| --- | --- |
| 모델 호출 | 24 |
| 입력 토큰 | 96,681 (18,716 · 13,995 · 22,671 · 11,157 · 30,142). 캐시 재사용 0 — 매 호출 처음부터 다시 읽음(T-013) |
| 출력 토큰 | 8,837 |
| 시간 · 비용 | 207초, 클라우드 한도 사용 0 |

| 클라우드 지휘자 (추정) | 위임 (이번 방식) | 직접 했다면 |
| --- | --- | --- |
| 출력 | 티켓 5개 3,526자(한글 815) + test_cmd → 약 2천 토큰 | 바뀐 코드 +110 · −6줄(diff 6,693 바이트)을 편집으로 → 약 2천 토큰 |
| 입력 | 워커 응답(diff · 요약 · 통계) 약 1.5만 자 → 약 5천 토큰 | 고칠 부분 읽기 · 테스트 결과 → 약 2~4천 토큰 |
| 합계 | **약 7천** | **약 4~6천** |

- 티켓을 정확히 쓰려고 고칠 코드를 미리 읽은 비용은 두 경우 모두 들어서 뺐다. 대화가 길어질수록 매 턴 앞부분을 다시 읽는 비용(캐시 읽기)도 턴 수가 비슷해 상쇄된다고 본다.
- **이번 시연에서 클라우드 토큰 절감은 없거나 약간 손해였다.** 티켓이 거의 코드 수준(함수 이름 · 위치 · 바꿀 줄)이라 티켓 쓰기 비용이 직접 코딩과 비슷했고, 워커 응답이 문맥에 더해졌다.
- 로컬은 약 10만 토큰으로 약 2천 토큰 분량의 편집을 했다. 무료이고 한도를 쓰지 않지만, 재사용 0 이 입력을 키운다.
- 위임이 클라우드 토큰을 줄이는 경우는 **워커가 많이 읽어야 하는데 명세는 짧은 일**(예: 실패 테스트를 주고 통과시키기)이다. 이번 이득은 토큰보다 기계적 편집을 넘기고 그동안 다른 일을 하는 데 있었다.

## 5. 결론

- 워커 주 경로(지휘자가 쪼개고, 테스트를 먼저 주고, 파일 1~2개 티켓으로)는 이번 실사용에서 그대로 통했다.
- 맡기지 않는 기준(큰 파일 · 테스트 작성 · 문서 판단)도 그대로 유지한다. 바꿀 근거가 없었다.
- 클라우드 토큰을 아끼려면 티켓을 코드 수준으로 쓰지 말고, 테스트로 명세를 대신할 수 있는 일을 고른다.
