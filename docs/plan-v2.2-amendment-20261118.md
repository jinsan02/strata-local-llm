## 5. KV 캐시 (지시 5절)

**확인 [문서·코드]:**
- 현재 실행 인자에 `--kv` 가 없다. `q36_engine.cu` 는 K · V 를 **FP32** 로 attention 층(10층)마다 `n_head_kv × ctx × head_dim` 씩 할당하고(1320~1333행), prompt attention 용 **FP16 사본** k16 · v16 을 따로 둔다(1393행). 메모리 계산식도 토큰당 `n_head_kv·head_dim·2·4·n_attn` + FP16 사본(1546~1562행).
- Flash-Next 의 `--kv int8|q4_0|k8v4|fp16` 처리는 q36 소스에 없다. → **기존 옵션으로 KV 형식 변경 불가 → 3차(엔진) 과제.** 1차에서는 할당 정책(`--kv-resident` 등)만, 적용 여부를 확인하고 본다.
- **기록 오류:** 러너가 원장 `kv` 열에 `int8` 을 상수로 적었다. 전 행 실제는 FP32(+FP16 사본). 측정값은 유효, 라벨만 틀림 → 정정 기록 (T-009, `LEDGER_SCHEMA.md`).

**미확인:** 실제 할당 바이트(엔진 로그 · nvidia-smi), MTP 층 KV, recurrent state(linear attention 30층) 크기, KV 를 줄였을 때 늘어나는 expert 수. 계산만 한 추정: 32K 에서 FP32 KV 약 1.3~1.5GB → FP16 이면 약 0.7GB 절약 → 층당 expert 약 +9 [미확인]. KV 감소율을 속도 향상률로 쓰지 않는다.

**링크 자료:** 네이버 블로그 본문은 도구 차단으로 미확인. 사용자가 같은 주제의 자료(TurboQuant 해설 · 원 논문)를 줘서 9.7 에서 검토했다.

## 9. 후속 전달문 반영 (11-18 오후, 3차 포함)

사용자가 7절 이후를 포함한 전달문을 다시 줬다. 위 1~8절과 겹치는 것은 그대로 두고, 새 내용과 정합화만 적는다.

### 9.1 상태 정합화

- 전달문의 "STATE 의 'X2 준비' 와 'X2 진행 중' 불일치" 는 이미 해소됐다 — X2 는 11:44~13:39 에 끝났고(원장 `x2_*` 84행, 커밋 `c3dbe1e`) STATE 는 'X3 준비' 다. 실행 중인 매트릭스는 없었다(확인 시점 프로세스 없음). 그 뒤 B1-1 을 새로 시작했다(9.3).
- 전원: X0 · X1 · XB = 균형 조정, X2 · B1 = 고성능. 서로 다른 전원 조건의 수치를 같은 A/B 로 합치지 않는다.
- 예산: 입력 최대 24,576 + 생성 8,192 유지. 실효 한도는 X2 처럼 입력 24,320 (+ 여유 256).

### 9.2 KV (Q3) — 전달문 지시와의 관계

전달문은 Q3 를 "런처 int8 vs 문서 FP32 불일치, 열린 질문" 으로 적었다. 이번 확인으로 **인자 전달 단계(인자 없음)와 할당 단계(FP32)는 [문서·코드] 로 닫혔다**(5절, T-009). 남은 것은 [미확인]:

| 구성 | 지금 아는 것 | 확인 방법 |
| --- | --- | --- |
| main attention K · V | FP32, 10층 x `n_head_kv x ctx x head_dim` (1320~1333행). 32K 에서 약 1.25GiB (계산) | 엔진에 할당 바이트 로그 추가 또는 nvidia-smi 차이 |
| prompt attention FP16 사본 | k16 · v16 1벌 (1393행) | 같음 |
| MTP 캐시 | MTP 블록 로딩 확인, 캐시 크기 미확인 | `mtp.cpp` 읽기 |
| recurrent state (linear attention 30층) | 미확인 | `q36_engine.cu` 읽기 |
| 작업 버퍼 · staging | 로그: prompt chunk 2048, staging 1.10GiB | 로그 |
| 읽기 · 쓰기 커널의 dtype · 패킹 | prefill 은 FP16 GEMM(FP32 누적), decode 는 미확인 | 커널 읽기 |

로그 기준 VRAM: 비전문가 가중치 4.40GiB, 그 뒤 여유 6.50GiB → expert 63/256 = 4.61GiB + staging 1.10GiB. 즉 KV · recurrent · 작업 버퍼 · CUDA 문맥이 약 5GiB 를 차지한다 (16GiB − 4.40 − 6.50, [측정+계산]). 이 5GiB 의 분해가 1차 · 3차 판단의 핵심이다. 지원 옵션으로 줄일 수 있으면 B1, 커널 · 레이아웃 수정이면 E1.

### 9.3 1차 (B1) 진행

- **B1-1 thinking 상한 (진행 중, 11-18 오후):** `matrix-b1t.ps1`. S0(예산 없음, answer_room 6,144) vs S1T3 · S1T4 · S1T6(요청 `reasoning_budget_tokens` 3,072 · 4,608 · 6,144), max_tokens 8,192, 짧은 입력, 과제 5개(새 `kv_store` = 모듈 전체를 쓰는 긴 답변) x 3회. config 와 note 에 실제 thinking 상한과 출처를 남긴다.
- 이후 순서는 6절 표. 설정 · 샘플링 변경에 따른 **출력 길이 · 품질 변화와 처리량 효과를 분리**해 기록한다 (예: thinking 을 줄여 빨라진 것은 엔진 개선이 아니다).
- **RAM (Q9):** working set · private · commit · page-in · 물리 SSD 읽기를 따로 기록한다. 원장 `ssd_read_mb` 는 서버 `/metrics` 의 `file_mb` 다 — 이것이 **엔진의 파일 읽기량인지, 실제 물리 디스크 읽기인지(OS 캐시 적중 포함 여부)** 는 [미확인]. 서버 소스와 Windows 성능 카운터(PhysicalDisk Read Bytes)로 대조한다.

### 9.4 2차 (Q1) — 전달문 5절 추가분

- M1 때문에 expert 배치가 달라지면 기록하고, M1 재튜닝은 **S2** 로 분리한다.
- RAM 보다 큰 원본의 변환 가능성을 도구 · 모델 경로(llama.cpp `llama-quantize` 의 mmap · 샤드 처리)에서 먼저 확인한다. Q4 → Q8 을 원본 복원으로 보지 않는다. runtime Q4 ↔ Q8 전환은 별도 과제.
- 보정 · 탐색 · 최종 평가 데이터를 분리하고, 실제 코드 테스트로 판단한다.

서버 H0 / HR 와 P0 는 run config · note 로 식별한다. 원장 열 · 과거 행 · 검사기는 이 문서를 이유로 바꾸지 않는다.

### 9.6 비교 · 최종 검증

기존 B0 · B1 · Q1 · E1 · C1 · F1, X0~X4 · XB ID 유지. 모델 · 엔진 · 서버 · 설정 · 전원 효과를 분리하고 C1 은 실측. tok/s 는 엔진 지표, reasoning/답변 지연 · 완료 · 품질은 따로. F1: 독립 50문항, 혼합 50회 · 60분, 본체 localhost / 노트북 호출 구분. 네이버 링크는 본문 확보 전까지 특정 기술로 추정하지 않는다.

### 9.7 TurboQuant 검토 (사용자 제공 자료, 11-18)

자료: 원 논문 arXiv 2504.19874 *TurboQuant: Online Vector Quantization with Near-optimal Distortion Rate* (Zandieh · Daliri · Hadian · Mirrokni, 2025-04-28 v1), 해설 https://sotaaz.com/post/turboquant-explained . 원 논문은 초록 · 페이지만 읽었다(본문 PDF 미독).

| 항목 | 내용 | 확인 |
| --- | --- | --- |
| 분류 | **KV 캐시 양자화** (토큰 제거 · 오프로딩 아님). 데이터 무관(보정 없음) 온라인 벡터 양자화 | 논문 초록 · 해설 |

**이 환경에 대한 판단 [계산 · 미확인]:**
- 분류: 기존 옵션 없음 → **3차 E1** (KV 저장 · 읽기 · attention 커널 수정). 1차 필수 과제 아님.
- 이득 상한이 작다: Qwen3.6 은 40층 중 10층만 full attention 이라 32K 에서 FP32 KV 가 약 1.25GiB. FP32 → 3.5비트면 약 1.1GiB, FP32 → FP16 만으로도 약 0.63GiB 절약. 늘어나는 expert 상주는 각각 층당 약 +15 / +8 (63 → 약 78 / 71, 256 중) 수준으로 추정. TG 개선폭은 X0 의 8K(77/256) 대 32K(63/256) 차이 약 8~15% 보다 작을 것으로 본다 — 실측 전에는 속도 향상률로 쓰지 않는다.
- 비용: decode 마다 역양자화 · 회전 연산, 커널 신규 작성, 수치 검증(긴 문맥 · MTP · 롤백). linear attention 30층의 recurrent state 는 대상이 아니다.
- 순서 제안: E1 에서 **FP16 KV(쉬움, 위험 작음) → 8비트 → TurboQuant 계열** 순. 9.2 의 5GiB 분해로 KV 비중을 먼저 실측한다.
