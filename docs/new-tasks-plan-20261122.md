# 새 과제 유형 계획 (11-22, STATE 25-5 · 26)

## 왜

- 지금 X3 6과제는 모두 **같은 저장소(pypa/packaging) · 같은 유형(명세를 읽고 기능 더하기)**이다. 30회 기준 점수(17 → 21)는 이 6과제 안에서 고른 설정이라 과적합 위험이 있다.
- 실제로 맡길 일은 버그 고치기 · 테스트 쓰기 · 리팩터링 · 여러 곳 연결이 섞여 있다. 유형이 바뀌면 필요한 도구(검사 · 개요)와 노력치도 달라질 수 있다.
- 그래서 **유형이 다른 과제 6개(Y 세트)**를 더해, 채택한 설정(H7 · card-coding · 노력치 · 도구)이 새 과제에서도 이기는지 확인한다. 하네스 튜닝에는 쓰지 않고 확인 전용으로 둔다(지금 D · E · F 와 같은 규칙).

## 유형과 후보 (각 유형 1~2개, 우선 6개)

| ID | 유형 | 무엇을 재나 | 후보 과제 | 저장소 | 채점 |
|---|---|---|---|---|---|
| Y1 | 버그 고치기(보고서) | 증상에서 원인 위치 찾기 | 사용자 보고(재현 코드 · 기대값 · 실제값)만 준다. 원인은 보고된 함수가 아닌 다른 함수에 있다(예: 버전 정렬 키 · 지정자 비교의 경계) | packaging | 숨은 테스트(보고 사례 + 주변 사례) + 회귀 |
| Y2 | 버그 고치기(실패 테스트) | 실패 로그 읽고 고치기 | 실패하는 공개 테스트 1개와 로그를 준다. 테스트는 고치지 말 것 | packaging | 그 테스트 + 숨은 변형 + 회귀 |
| Y3 | 테스트 쓰기 | 테스트로 동작 고정 | 기존 함수 하나(예: `canonicalize_version`)에 대한 테스트 파일을 새로 쓴다 | packaging | **돌연변이 채점**: 원본에서 통과 + 미리 만든 돌연변이 N개 중 몇 개를 잡나 |
| Y4 | 리팩터링 | 동작을 바꾸지 않고 구조 바꾸기 | 중복 로직을 함수 하나로 뽑고 호출부를 모두 바꾼다 | packaging | 전체 회귀 + 숨은 구조 검사(새 함수 존재 · 호출부가 그것을 씀) |
| Y5 | 여러 곳 연결 | 한 기능을 3~4곳에 일관되게 | 새 옵션 하나를 정의 · 파싱 · 검증 · 출력에 모두 반영 | flask (SWE 세트 환경 재사용) | 숨은 테스트 + 회귀 |
| Y6 | 작은 기능 (다른 저장소) | 저장소가 바뀌어도 되나 | 지금 6과제와 같은 유형을 다른 저장소에서 | flask | 숨은 테스트 + 회귀 |

- 크기는 지금 과제와 비슷하게(파일 1~3개, 수십 줄). 큰 파일(1,000줄 이상)이 하나 이상 들어가게 해 high · 도구 효과도 보이게 한다.
- 저장소를 하나 더(flask) 쓰는 이유: packaging 의 구조 · 이름에 익숙해진 설정이 아닌지 본다. flask 는 SWE 세트(`x3sh*`)로 conda 환경이 이미 있다.

## 하네스에 필요한 것 (서버 없이 만들 수 있음)

| 항목 | 내용 | 쓰는 과제 |
|---|---|---|
| `setup_patch` | 작업 복사본을 만든 뒤 과제 전용 패치를 먼저 적용(버그를 심거나 실패 테스트를 넣음). 모델에게는 보이지 않는 git 커밋으로 만들어 diff 에 섞이지 않게 한다 | Y1 · Y2 |
| 돌연변이 채점 | `private/mutants/*.patch` 를 하나씩 적용하고 모델이 쓴 테스트 파일을 돌려 실패하면 '잡음'. 원본에서 실패하면 0점. 통과 기준은 예: N개 중 70% 이상 | Y3 |
| 저장소별 설정 | `task.json` 에 `repo` · `commit` · `python` · 테스트 명령을 두고, 지금 packaging 고정값은 기본값으로 | Y5 · Y6 |
| 검증 스크립트 | 기준 커밋 실패 · 참조 패치 통과 · 회귀 통과(지금 `validate_def.py` 와 같은 표) | 전부 |

## 순서

1. 하네스 확장(`setup_patch` · 돌연변이 채점 · 저장소별 설정)과 자체 점검. 서버 불필요.
2. 과제 6개 작성: 프롬프트 · 참조 패치 · 숨은 테스트(· 돌연변이) · 검증. 서버 불필요. 측정 체인이 없을 때 검증을 돈다(CPU 를 써서 측정을 흔들지 않게).
3. 측정: 지금 기준(H7 + card-coding, medium)과 채택 후보(노력치 · 도구)를 Y 세트 6과제 x 5회로 비교.
4. 판정: Y 세트에서도 −1 규칙을 지키면 채택을 유지한다. Y 세트에서만 떨어지면 그 유형을 따로 본다.

## 주의

- 숨은 테스트 · 참조 패치 · 돌연변이는 모델 입력과 작업 복사본에 넣지 않는다(지금 규칙과 같음).
- `final_eval/` 은 읽지도 쓰지도 않는다. Y 세트도 최종 평가(F1)에 쓰지 않는다.
- 저장소 원 코드를 과제 파일에 복사하지 않고, 실행할 때 고정 커밋을 clone 한다.
